# site

Paths below are relative to `site/`.

A webradio: backend Bun + Elysia, frontend Vite + React, pnpm monorepo orchestrated by Turbo. Versions live in the `package.json` files; setup in the README. Commit scopes, CI and deploy-by-merge are in the root `CLAUDE.md`.

## Conventions

- **Branches** — short kebab-case with a type prefix (`feat/like-track-batch`, `fix/cors-prod`).
- **Code style** — named exports rather than default ones.

## Workflow rules

- **A site PR is tried in Chrome before its merge**, at 1280 and 390 px wide, on the local stack (`pnpm stack`, README « La pile locale, en une commande »).
- Checks: `.husky/pre-push` is the list the CI runs (typecheck, lint, knip, contrast, tests, build); frontend tests `pnpm --filter=@aubesonore/frontend test --run` (without `--run`, Vitest watches); backend tests `pnpm --filter=@aubesonore/backend test` (mocks).
- Tests against a real Postgres (`*.db.test.ts`): `pnpm --filter=@aubesonore/backend test:db` with `DATABASE_URL` naming a disposable database whose name ends in `_test`, its schema from `db:push` (`src/test/pg.ts` refuses any other). `db:push` reads `DATABASE_URL`, else `.env`: export the test database's first, or it syncs `schema.ts` onto the database `.env` names.
- `.husky/pre-push` mirrors most of the CI (see the file); the Postgres tests, `scripts/*.test.sh`, `format:check` and the audit run only in CI.
- Frontend i18n messages (`apps/frontend/src/paraglide/`) are generated by `compile:i18n`, not committed: a bare `tsc` or `eslint` in `apps/frontend` fails on missing imports. Go through the package scripts, which compile them first.
- `master` merges only when the required CI checks pass; no human review is required.
- Valibot validates at the HTTP boundary.

## Deployment (self-hosted, pull-based)

How the box deploys, rolls back and is installed: README « Déploiement » and `scripts/deploy.sh`. What stays a rule when changing the site:

- **Leave `schema.ts` alone in a PR that changes no schema.** The deploy compares the file and stops on any change without its own migration, a comment included; when a comment there must follow the code, acknowledge right after the merge (README « Déploiement »).
- **A failed deploy is not retried**: `scripts/deploy.sh` records it (`aubesonore.failedTarget`) and waits for a newer `master`.
- **Check a compose change** with `docker compose config` against a production-like `.env` before merging. AzuraCast keeps its own compose, never merged into this one: its updater manages it, and a site deploy must never restart the radio.
- Container logs go to the journal (`compose.yaml`, `logging`); the per-request `http` line (`lib/requestLog.ts`) never logs the query string.

### Database backups

`scripts/backup-db.sh` (from `aubesonore-backup.timer`; schedule, destination and retention are in the script and unit) writes to a physically separate disk from the one holding the Docker volume, so a single-disk failure cannot take both.

- The script refuses to dump an unhealthy container and deletes any archive `pg_restore --list` cannot read: a corrupt dump looks like a backup.
- Dumps are `chmod 600` in a `700` directory: they carry user emails and auth rows, on a shared box.
- To restore: `docker exec -i aubesonore-db pg_restore -U aubesonore -d <db> < <dump>`. Rehearse into a throwaway database, never straight over production.
- The `musilogy` schema is left out of the dump: it is reference data reloaded with `musilogy load` (`.claude/rules/musilogy.md`). Drizzle never touches it (`apps/backend/drizzle.config.js` only describes `public`).

## Backend env

Env vars are read only in `apps/backend/src/config/env.ts`; never read `process.env` elsewhere in the app. The one-off scripts of `src/scripts/` read their own.

## Working with Better Auth

- Config lives in `apps/backend/src/lib/auth/index.ts`, rate limits in `lib/auth/limits.ts`.
- Email verification is required for new accounts, which makes SMTP load-bearing for registration: `config/env.ts` refuses to boot in production when `SMTP_HOST` is unset and `DISABLE_EMAILS` is not explicitly `true`. Without that guard the app answers 200 everywhere while no one can create an account.

## Working with Drizzle

- Schema = `apps/backend/src/db/schema.ts`; indexes are declared inline there.
- `src/db/migrate.ts` applies, at boot and in name order, every `drizzle/*.sql` not yet recorded. Every new migration must be idempotent SQL (`IF NOT EXISTS` / `IF EXISTS`), since the runner may meet a schema that already has it.
- `db:push` syncs `schema.ts` straight to the connected DB and can drop columns. The repo keeps no drizzle snapshot meta, so `drizzle-kit generate` cannot work: migrations are hand-written.

## Working with artist enrichment

The artist profile (`artistPage.routes.ts`) combines several sources, each isolated, cached, and allowed to fail on its own. One artist, one page: Musilogy's sections live on the artist page too. Product rules are in `../docs/vision.md`.

- **The page always answers** (vision §4.6). `artist_profile` stores the last answer of each live source. Sources return a `Lookup` (`lib/lookup.ts`): a definitive miss clears its section; a failure or timeout keeps the stored one and leaves `refreshed_at` as it was, so the next view retries.
- What the listener kept of the artist comes from the liked tracks the frontend already loads; no extra route.
- **Identity first.** `artistResolver.resolveArtist` strips `feat.`/`ft.`/`featuring` only. Never split on `&`, `+` or `,`: that destroys "Simon & Garfunkel" and "Earth, Wind & Fire".
- **Slugs are permanent** (`services/artistSlugs.ts`). A slug is given the first time the site publishes the address, never before, and is never changed nor handed to another page (« Cool URIs don't change »). Homonyms are ranked by `musilogy.artist_homonym_rank`; a page Musilogy cannot rank keeps its MBID rather than take a better-known homonym's name. A page answers at its `profile.slug`; any other key naming it answers a 301 there. The localized path is a Paraglide `urlPatterns` entry in `apps/frontend/scripts/paraglide-options.mjs`, shared by Vite, Vitest and `compile:i18n`.
- **A page for every artist Musilogy knows, never for a typed name** (vision §5). `/api/artist/resolve` is public, and a page for any typed name would let anyone publish text under aubesonore.fr. An MBID the dump does not hold is a 404; while Musilogy is not loaded, 503. Indexing threshold: `discoveredArtists.ts`.
- **An ISRC counts only for the played track** (vision §4.4). The resolver reads it from `radio_play` or the track on air, never from a caller, so `/resolve` cannot be handed another recording's code. An ISRC answer (MusicBrainz or Deezer) must match the played title and credit the played name; unchecked, it bound artists to the wrong identity in production.
- `artist.identified_by` (`'isrc'` or `'name'`): a name-bound row is re-identified once a play carries a checked ISRC. `writeIdentity` writes an identity whole and drops the stored `artist_profile` when it changed.
- **Never bind by name alone.** Deezer binds through a played title first; a name search binds only an artist with no exact homonym. MusicBrainz binds through the Deezer link, else a unique recording of exactly the played title credited under the played name. A source failure (for Deezer: network, 5xx, 429, or an `error` body with HTTP 200 other than code 800) is never stored as "unknown": nothing is persisted and the next call retries.
- **The MBID is the bridge to Musilogy** (vision §4.4). `ensureMbid` writes it once found; nothing found or a failure writes nothing. Catch-up: `docker exec aubesonore-backend bun run artists:resolve` (sequential, it shares MusicBrainz's rate with the running backend).
- A kept track is tied to its artist (`liked_tracks.artist_id`) through the play it was kept from (`linkKeptTrack`); a track the antenna is not known to have played stays untied, since the like route takes any title.
- **Source constraints.** MusicBrainz: a 1 req/s throttle and a User-Agent with a contact are hard API requirements. Deezer: identity and listening links only (its terms allow private use, vision §2.5). A dissolved country or a MusicBrainz region such as SU or XW is not named (Intl reads SU as Russia). A person's MusicBrainz begin date and area are a birth, never shown as a career. A Commons file without a licence is no photo.
- **No source, licence or tool is named on a listener's page** (vision §1.2); credits live on the legal page. Exceptions: the Wikipedia opening links its article (CC BY-SA), and a photo's credit is shown behind a small © on the portrait (CC BY-SA §4c).
- `radio_play` is the floor: no external source knows what this radio played. It is unique on AzuraCast's `sh_id` so a restart does not record the current track twice.
- Services behind an artist page or live calls use `TtlCache` + `createSingleFlight`, so a cold popular page triggers one upstream call, not one per listener.
- **OG tags**: `services/artistPageRender.ts` reads the build's empty shell (`app.html`), never `index.html` (the pre-rendered home page), revalidating it by ETag (a shell kept past a deploy points at deleted assets). It rewrites head tags in place with `HTMLRewriter`; appending would leave the home page's canonical. Meta text: `services/templates/artistMeta.ts`. `og:image` is restricted to the Cover Art Archive: a link preview could not carry a Commons photo's credit.
- **Images are hotlinked (Apple, Deezer, Commons), except the covers of the cover store**: the Cover Art Archive's, the antenna's and the kept tracks' copies, each made once as WebP and kept as a file nginx serves (`services/coverStore.ts`, `apps/frontend/nginx.conf` `/covers/`, `apps/frontend/src/lib/artwork.ts`), because direct thumbnails were slow and often failed. The store's keys are ids and sizes, checked by nginx and the backend: it never fetches a URL it was given. The Cover Art Archive copy is the owner's legal choice; keep the legal page's credit and removal offer. A removal is a line in `services/coverBlocklist.txt` (README « Retirer une pochette »): a blocked cover is never served, fetched nor stored again, and its files leave the volume at boot; copies already in browsers or at Cloudflare's edge are not recalled by that. Covers fade in (`useFadeIn`) only when they mount still loading: never hidden before the script runs, never on a server-drawn priority image, never on an image whose source changes.

## Working with Musilogy

Musilogy's data is loaded into the `musilogy` schema: `musilogyService` calls only the SQL functions of `../musilogy/docs/conception.md` §4, never the tables.

- **A section not loaded yet is `null`, never empty.** A function Postgres does not know (`42883`, or the schema missing) makes its section `null` and the page leaves it out; the card and the search answer 503, and the search says Musilogy is not available, never that it is « reloading » (a load may not come).
- An end date is shown only when declared, never inferred from a last album; a start read from the first album says so.
- **Close artists come in three tabs, none filtering another** (vision §2.2): « Même son » (`artist_same_sound`), « Écoutés ensemble » (`artist_colisten`) and the filiation (bands, member projects, other names, `artist_credits`), each in the order its function gives, never re-sorted. Declared influences and labels are not shown.
- Albums and EPs are paged (`Releases.tsx`): drawing thousands at once froze the page.
- Every artist link goes through `pagePathOf`. A section with nothing in it is left out, never titled over an absence. A single year reads alone (« 1992 »), never « de 1992 à 1992 ».
- `MusilogyTimeline`: the owner rejected a light band behind the rows. The artist's own row is `aria-hidden` (the page header says its years).
- The search page is `X-Robots-Tag: noindex` (nginx).

## Casting

- **Chromecast** uses AubeSonore's Custom Web Receiver (`lib/cast/chromecast.ts`), never the Default Media Receiver: the receiver follows the track on air itself so the TV's title and cover change while the stream plays. **AirPlay** is Safari's picker on the `<audio>` element (`lib/cast/airplay.ts`).
- **The receiver is `cast/receiver.html`**, a second Vite entry: no React, no service worker (a plugin in `vite.config.ts` strips what vite-plugin-pwa injects), hex colours (older Cast devices lack oklch). It plays the station as a LIVE stream without Pause: resuming plays the buffer behind the antenna. nginx serves it with its own CSP.
- One Diffuser button (`CastControl`) for both, rather than Google's `<google-cast-launcher>`, which hides itself without a device and knows no AirPlay. The sender SDK loads in Chromium only.
- Test on the devices registered in the Cast console before publishing the app: publishing makes it reachable from every Cast device.

## Security baselines

- Never `fetch()` a user-supplied URL. The app has no URL guard: a route that must fetch one needs one first, blocking private IPv4/IPv6 and link-local (`169.254.0.0/16` = cloud metadata) and enforcing `https` in prod.
- The `securityHeaders` Elysia plugin must stay mounted in `index.ts` (CSP, HSTS in prod, etc.).

## Track links and YouTube

- `services/trackLinksService.ts` memoizes lookups in `TtlCache`; a result cut short by a failed lookup is not cached.
- Track links come from each platform's API; Odesli's keyless API is closed, don't reintroduce it. A kept track's Deezer link comes from its ISRC (`/track/isrc:`), which finds the very recording the antenna plays; the title search, which often picks another version, is only the fallback.
- **YouTube** (`youtubeService`, `youtubeLinks`): a stored link is a search until an Art Track is verified. A result counts only when its « Title · Artist » line is the kept track (feat. and remaster set aside, never a looser match).
- **YouTube's limits are load-bearing** ([quota costs](https://developers.google.com/youtube/v3/determine_quota_cost)): search.list has its own small daily bucket. API data must be refreshed or deleted within 30 days (Developer Policies III.E.4.d): a link older than 30 days is never served. `YOUTUBE_API_KEY` never reaches a log, not even in a network error's URL.

## What not to do

- Don't write per-package `pnpm-lock.yaml` or `bun.lock`: the site's root `pnpm-lock.yaml` is authoritative.
- Don't disable `requireEmailVerification` unless a temporary migration window needs it, and roll back immediately.
- Don't bypass the `securityHeaders` plugin or Better Auth's rate limits.

## ESLint typed rules

Typed rules (`no-floating-promises`, `no-misused-promises`, …) are errors on `apps/*/src` and `packages/*/src` (`eslint.config.js`). Intentional fire-and-forget promises get `void`.

## Dependencies

Renovate owns dependency PRs and auto-merges the safe ones (`../renovate.json`). Dependabot is kept for security alerts only: don't re-add the root `.github/dependabot.yml`. A major bump goes in its own PR.

## Scaling

Caches and rate-limit buckets are in-process on purpose (`TtlCache` behind the `CacheStore<V>` surface a Redis store would keep). Tiers and their triggers are in `docs/scaling-roadmap.md`; don't build a tier before its trigger fires.
