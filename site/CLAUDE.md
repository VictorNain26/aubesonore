# AubeSonore — Project Instructions for Claude

A webradio: backend Bun + Elysia, frontend Vite + React 19, pnpm monorepo orchestrated by Turbo.

## Stack at a glance

| Layer    | Tech                                                            |
| -------- | --------------------------------------------------------------- |
| Backend  | Bun 1.3, Elysia 1.4, Drizzle 0.45 + PostgreSQL, Better Auth 1.6 |
| Frontend | React 19.2, Vite 8, Tailwind 4.3, Zustand 5                     |
| Tooling  | pnpm 10.34, Turbo 2.10, ESLint 9 flat, Vitest 4.1 + bun test    |

The README has setup details; this file is for Claude.

## Conventions

- **Commits** — enforced by `.husky/commit-msg` + `commitlint.config.js`. Scope = app or module touched.
- **Branches** — short kebab-case (`feat/like-track-batch`, `fix/cors-prod`). The default branch is `master`; changes land through a PR.
- **Code style** — Prettier (`.prettierrc.json`). Named exports preferred over default. TypeScript strict everywhere (see `tsconfig.base.json`).
- **File naming** — backend uses dotted (`track.routes.ts`, `trackService.ts`), frontend uses PascalCase for components (`MyTracksView.tsx`) and camelCase for lib/hooks. Each layer is consistent internally.

## Workflow rules

- Checks: `pnpm typecheck && pnpm lint`; frontend tests `pnpm --filter=@aubesonore/frontend test --run` (without `--run`, Vitest watches); backend tests `pnpm --filter=@aubesonore/backend test`. `.husky/pre-push` runs the full CI mirror on every push.
- Frontend i18n messages (`apps/frontend/src/paraglide/`) are generated by `compile:i18n`, not committed: the frontend `lint` and `typecheck` scripts compile them first, so a bare `tsc` or `eslint` in `apps/frontend` fails on missing imports. Go through the scripts.
- **`master` is branch-protected** — a PR merges only when the 5 required CI checks pass: the site's `Quality (lint, typecheck, test, audit)`, `Backend tests (bun)` and `Build all`, plus `Pipeline (ruff, mypy, pytest)` and `musilogy (ruff, mypy, pytest)`, which run on every PR; no human review is required.
- Valibot/TypeBox validate at the HTTP boundary.

## Deployment (self-hosted, pull-based)

The stack runs on the maintainer's own box. Merging to `master` is the whole deploy action — `scripts/deploy.sh`, driven by a **systemd user timer**, polls `git ls-remote` every 2 minutes and promotes `origin/master` when it moves (`uv sync --locked` of `pipeline/.venv` → `git merge --ff-only` → the same sync again when `pipeline/` changed → `docker compose up -d --build` → wait for every healthcheck → prune images older than 72h).

- **Pull-based on purpose.** The repo is public, and GitHub warns that "forks of your public repository can potentially run dangerous code on your self-hosted runner machine" ([docs.github.com](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/manage-access)) — so no self-hosted runner, and no inbound webhook to expose. Polling needs no credential and no open port.
- **Schema changes ship with a migration.** The backend applies new `apps/backend/drizzle/*.sql` files at boot (`src/db/migrate.ts`, idempotent SQL only), so a change to `schema.ts` that adds one deploys on its own. A change (one squash or merge commit on `master`) that touches `schema.ts` without adding its own migration stops the deploy; whether the migration matches the schema is the PR review's job. To unblock: apply it by hand, acknowledge with `git -C ~/aubesonore config aubesonore.appliedSchema <blob>` (the script prints the exact command), then `systemctl --user start aubesonore-deploy`.
- **Only a clean `master` deploys.** `~/aubesonore` is the production checkout: on another branch, or with a modified or untracked file, the script refuses (exit 1, the unit shows failed) instead of fast-forwarding someone's branch. Work happens in a worktree.
- Install once: symlink `scripts/systemd/*` into `~/.config/systemd/user/`, then `systemctl --user enable --now aubesonore-deploy.timer`. Requires user lingering (already on). Logs: `journalctl --user -u aubesonore-deploy`.

### Database backups

`scripts/backup-db.sh` runs nightly at 03:30 from `aubesonore-backup.timer` and writes a `pg_dump -Fc` archive to `/media/plex/.backups/aubesonore`, retained 14 days. That path is a **physically separate disk** (`sda1`) from the NVMe holding the Docker volume — a single-disk failure must not take both.

- The script refuses to dump unless the container reports `healthy`, and deletes any archive `pg_restore --list` cannot read: a corrupt dump is worse than none, because it looks like a backup.
- Dumps are `chmod 600` in a `700` directory — they carry user emails and auth rows, on a box shared with other services.
- To restore: `docker exec -i aubesonore-db pg_restore -U aubesonore -d <db> < <dump>`. Rehearse into a throwaway database, never straight over production.
- The `musilogy` schema is left out of the dump (`--exclude-schema`): it is reference data owned by `musilogy/`, reloaded with `musilogy load` (`musilogy/CLAUDE.md`). Drizzle never touches it — `drizzle.config.js` only describes `src/db/schema.ts`, in `public`.

## Backend env

Env vars are read only in `apps/backend/src/config/env.ts`; never read `process.env` elsewhere in the app.

## Working with Better Auth (1.6)

- Config lives in `apps/backend/src/lib/auth/index.ts`. Cookies are `secure` + `httpOnly`; `sameSite: 'none'` in prod, `'lax'` in dev.
- Rate limits are tuned: 5/min sign-in, 3/min sign-up & forget-password.
- Email verification is **required** for new accounts (`requireEmailVerification: true`). That makes SMTP load-bearing for registration, so `config/env.ts` **refuses to boot in production** when `SMTP_HOST` is unset and `DISABLE_EMAILS` is not explicitly `true`. Without that guard the app answers 200 everywhere while no one can create an account — which is exactly what happened until July 2026. Setting `DISABLE_EMAILS=true` in production is legal but logs `email.disabled_in_production` at every start.
- Google + Spotify OAuth providers configured.

## Working with Drizzle

- Schema = `apps/backend/src/db/schema.ts`; all indexes are declared inline there.
- `apps/backend/src/db/migrate.ts` runs at backend boot and applies every `apps/backend/drizzle/*.sql` not yet recorded in `__app_migrations`, in name order. `0000`–`0003` are baseline, recorded without running. **Every new migration must be idempotent SQL** (`IF NOT EXISTS` / `IF EXISTS`), since the runner may meet a schema that already has it.
- `bun db:push` syncs `schema.ts` straight to the connected DB and can drop columns. Don't use `bun db:generate`: the repo keeps no drizzle snapshot meta (no `apps/backend/drizzle/meta/`); new migrations are hand-written.

## Working with artist enrichment

The artist profile (`GET /api/artist/page/:slug`, document route `/artiste/:slug`, `/en/artist/:slug` in English) answers who the artist is in a few words, and nothing more: a portrait, one line of facts, the opening of a Wikipedia article or, without one, the facts said in a sentence (`portraitSentence`), what the listener kept of the artist, where to listen. Each source is isolated, cached, and allowed to fail on its own. **One artist, one page**: the artist page also carries Musilogy's sections (`MusilogySections`, read by the artist's MBID), each only when it holds something; the profile's `playedOnRadio` is no longer shown.

- **The page always answers** (`docs/vision.md` §4.6). `artist_profile` stores the last answer of each live source: the Deezer portrait and the Wikipedia openings. The facts, the listening links and the Wikidata item are the dump's, read from musilogy at each view (`getArtistIdentity`: `artist_card` and `artist_urls`, cached an hour); while musilogy is not loaded the page has no facts, keeps its stored openings and stays stale so the next view retries. The first view of an artist waits for the sources (6 s each at most); later views read the stored profile, and one older than 7 days is served as it is while `refresh` asks again behind the answer (single-flight per artist). Sources return a `Lookup` (`lib/lookup.ts`): a definitive miss clears its section, a failure or a timeout keeps the stored one and leaves the profile's `refreshed_at` as it was, so the next view retries. A restart or a deploy no longer sends a cold page to Deezer and Wikipedia.
- **What the listener kept** comes from the liked tracks the frontend already loads at sign-in, filtered on `artistId`; no extra route.

- **Identity first.** `artistResolver.resolveArtist` turns a messy AzuraCast string into a canonical id persisted in the `artist` table, so URLs stay stable across restarts. It strips `feat.`/`ft.`/`featuring` only — **never split on `&`, `+` or `,`**, that destroys "Simon & Garfunkel" and "Earth, Wind & Fire". The key is `normalizeArtistName` (letters and digits of every script, so "Кино" has a page).
- **One slug per artist, for good.** `artist_slug` gives each played artist the first free slug of its name, alone or suffixed (`cassius`, `cassius-2`), in the same transaction as its row; a slug is never changed nor handed to another artist, so a shared or indexed address keeps working. The old addresses `/artist/<id>/…` answer a 301 to the page (`artistPage.routes`). The localized path (`/artiste` ↔ `/en/artist`, like `/connexion` ↔ `/en/sign-in` and `/mentions-legales/` ↔ `/en/legal/`) is a Paraglide `urlPatterns` entry in `scripts/paraglide-options.mjs`, the one set of options the Vite build, Vitest and `compile:i18n` share.
- **A page for every artist Musilogy knows, never for a typed name** (`docs/vision.md` §5). An artist the antenna played (`radio_play`, or the track on air) has a row and a slug; any other MBID the dump holds has a page at `/artiste/<mbid>`, made at each view from Musilogy (`unplayedProfile`: facts, links, first record cover) and the live sources' cached answers (Deezer portrait, Wikipedia opening). No row is stored for it, so a crawler walking Musilogy fills no table. Such a page answers `X-Robots-Tag: noindex` until the richness threshold gives it a slug; the MBID of a played artist answers a 301 to its slug; an MBID the dump does not hold is a 404, and while Musilogy is not loaded the page answers 503. `/api/artist/resolve` is public, and a page for any typed name would let anyone publish text under aubesonore.fr. The page API has its own rate bucket (60/min per IP), apart from the resolver's 10: a walk from artist to artist opens a page every few seconds.
- **The thread's links are a lookup, never a resolution.** `POST /api/artist/pages` (`services/artistPages.ts`) answers the pages already in the `artist` table for a day of names in one indexed query; it never creates an artist nor calls a source, so it gets its own rate bucket (30/min) apart from `/resolve` (10/min). POST because a day of names does not fit in a URL.
- **The ISRC identifies first, once checked** (`docs/vision.md` §4.4). The pipeline writes each antenna file's ISRC (ID3 `TSRC`), AzuraCast reports it as `song.isrc`, `nowPlaying` keeps it when well formed (`lib/isrc.ts`, ISO 3901) and `radio_play.isrc` stores it. The resolver reads it from `radio_play` or the track on air, never from a caller, so `/api/artist/resolve` cannot be handed another recording's code. **An ISRC answer counts only for the played track**: `findRecordingsByIsrc` must give a recording of the played title (`sameTitle`: normalized, versions aside) crediting the played name, `findTrackByIsrc` (Deezer's `GET /track/isrc:<code>`, measured, not found in its public documentation) the same. Unchecked, it gave Paul McCartney Wings' identity, Daniel Avery ANNA's and The Pirouettes another Deezer artist (production, 2026-10-04). `identify` then completes one identity through the other (the Deezer link MusicBrainz declares, exactly one, else none), and only then falls back on the name bound to the played title. A source failing writes nothing and the next play retries.
- **`artist.identified_by`** says whether a checked ISRC (`'isrc'`) or only the name (`'name'`) gave the identity. A name-bound row is re-identified once a play of it carries a checked ISRC (Can had been bound to a one-album homonym). `writeIdentity` writes an identity whole, keeping nothing of the one it replaces, and drops the stored `artist_profile` when it changed. When another row already holds that identity (two spellings of one artist), the row keeps its own and the conflict is logged; a new spelling whose identity another row holds resolves to that row's page.
- **The name is the last resort**, for a play without an ISRC that no source knows. Deezer binds through a title the antenna played, never by name alone: `searchArtist` searches the played track and keeps its artist when the name is equal once normalized; only when no track settles it does a name search bind, and only an artist with no exact homonym. Measured on the 145 artists played by 2026-10-02: a name search ranked a homonym first for 11 of them (Cassius, De La Soul, M.I.A.…). A Deezer failure (network, 5xx, 429, or an `error` body sent with HTTP 200 other than code 800 "no data") is never stored as "unknown": nothing is persisted and the next call retries. MusicBrainz then binds through the Deezer link (`findMbidByDeezerId`), never by name: nine artists are called Cassius.
- **The MBID is kept: it is the bridge to Musilogy** (`docs/vision.md` §4.4); the page reads the stored `artist.mbid`. For a name-bound row, `ensureMbid` (`artistResolver`) writes it once found: nothing found or MusicBrainz failing writes nothing, so a later call retries; a unique violation (two spellings of one artist) is logged, any other error propagates. Every played artist is resolved at its first play by `antennaWatcher`, after the play is recorded so the resolver sees its ISRC, not when a listener opens its page. `docker exec aubesonore-backend bun run artists:resolve` catches up: it gives earlier plays their ISRC from the station's media (`GET /station/{id}/files`, matched on normalized artist and title), resolves every played artist, identifies every known artist again from scratch (`reverifyArtist`, from its latest play or else a track kept of it), then ties the kept tracks (sequential, one MusicBrainz request per second).
- **A kept track is tied to its artist** (`liked_tracks.artist_id`). `linkKeptTrack` (`trackService`, run after each like, not awaited) finds the play it was kept from (`findPlay`: same artist and title once normalized), takes that play's ISRC and the artist `resolveArtist` gives. A track the antenna is not known to have played stays untied: the like route takes any title. `artists:resolve` ties the tracks kept before plays were recorded through their exact Deezer match (`searchDeezer`), whose ISRC stands for the play (`resolveKeptArtist`, never reachable from a route).
- **Sources**: `deezerService` (portrait — keyless; without one, the cover of the first album or EP at the Cover Art Archive, hotlinked, and the page's generated wave when that fails to load), `musicbrainzService` (identification only, `docs/vision.md` §4.3: recordings by ISRC, the Deezer link both ways; **1 req/s throttle and a User-Agent with a contact are hard API requirements**), musilogy (facts, listening links, the Wikidata id: one source for every page, `docs/vision.md` §4.5; a dissolved country or a MusicBrainz region such as SU or XW is not named, Intl would read SU as Russia), `wikipediaService` (Wikidata sitelinks → `page/summary` of the article in the page language, else the other one; disambiguation pages are dropped; the first sentence, plus the second while the whole stays within 300 characters). A person's MusicBrainz begin date and area are a birth, never shown as a career. Wikipedia text is CC BY-SA: the page links the article (« Lire la suite sur Wikipédia ») and the legal page's credits name the licence — **no source, licence or tool is named on a listener's page** (`docs/vision.md` §1.2); credits live on the legal page.
- **`radioPlayService` is the floor.** No external source knows what this radio played, so `antennaWatcher` records every new track in `radio_play`, unique on AzuraCast's `sh_id` so a restart does not record the current track twice.
- Every service uses `TtlCache` + `createSingleFlight` (plus Deezer's 429 breaker and MusicBrainz's throttle), so a cold popular page triggers one upstream call, not one per listener.
- **OG tags**: `artistPage.routes` reads the build's empty shell (`app.html`) from the frontend container — never `index.html`, the pre-rendered home page — revalidating it on every request with its ETag (a shell kept past a deploy points at deleted assets), and rewrites its head tags **in place** (title, description, canonical, `og:*`, `twitter:*`) with `HTMLRewriter`; appending would leave the home page's canonical in place. `og:image` is restricted to an allowlist of Deezer CDN hosts. An unknown id answers 404; pages are `Cache-Control: no-cache` like every HTML page of the site.
- Deezer images are **hotlinked, never re-hosted**.

## Working with Musilogy

Musilogy is the artist page's part that leads elsewhere (its close artists, influences, bands and their projects, `MusilogySections`) and its search (`/musilogy`, `/en/musilogy`). The old artist addresses `/musilogy/<mbid>/…` answer a 301 to `/artiste/<mbid>` (nginx), and in the app `MusilogyPage` redirects them the same way (`docs/vision.md` §2). Its data is musilogy's, loaded into the `musilogy` schema: `musilogyService` calls only the SQL functions of `musilogy/docs/conception.md` §4, never the tables.

- **A section not loaded yet is `null`, never empty.** A function Postgres does not know yet (`42883`, or the schema missing) makes its section `null` (`neighbours`, `influences`, `releases`, `bands`, `memberProjects`, `otherNames`) and the page leaves that section out (Musilogy's own page says once that it has nothing to show when every section is out); the card and the search answer 503 instead, and the page says Musilogy is not available — never that it is « reloading », which would promise a load that may not come. musilogy changes only when it is loaded again: answers are cached for an hour, swept like every cache (`index.ts`), one query per artist however many ask (`createSingleFlight`).
- **Dates say where they come from**: a start read from the first album says so, an end is shown only when declared (241 of 288 played artists had an end inferred from a last album). Neighbours whose start MusicBrainz does not know get their own list.
- **No source on the page** (`docs/vision.md` §1.2): no MusicBrainz, ListenBrainz, Wikidata or licence is named or linked; the legal page's credits name them all once. A declared influence keeps its Wikidata statement in the data (`statement`), never as a link on the page.
- **Proximity is never an influence.** Neighbours come from ListenBrainz co-listening, sorted by musilogy into before / alongside / after by their start year (±3 years); only Wikidata's declared influences are called influences. The page says so in a listener's words: neighbours are « ceux qu'écoutent les mêmes auditeurs », influences are those the artist cited.
- **Bands and projects**, three sub-lists rather than MusicBrainz's relation types (`docs/vision.md` §2.4): members of a group or groups of a person, with their years (`artist_bands`); the members' other bands and names, two steps away and only those with a record, each saying which members lead there (`artist_member_projects`); other names, on one line, each saying what it is to the artist (`artist_other_names`).
- **Albums and EPs** (`artist_releases`, `Releases.tsx`): albums, then EPs past the first eight on demand, each with its Cover Art Archive thumbnail (`front-250`, hotlinked, the wave when none) and its year. On the artist page they come after the listening links and before what the listener kept, the order of `docs/vision.md` §2.4.
- Every artist link goes to the artist's one page (`pagePathOf`): its slug when the antenna played it (`played`, read from `artist.mbid`), its MBID otherwise. A section with nothing in it is left out, never titled over an absence.
- **The map** (`MusilogyMap`) draws the 40 closest neighbours in time, laid out by `layoutMap` (a pure function): years left to right, the artist's span on the axis with its name, each neighbour at its start year, the closest on the rows nearest the axis; a label with no free row is left to the lists. Labels are Geist Mono at 12 units, whose advance (0.6 em, measured in Chromium) makes their width known — a CSS letter-spacing on the SVG would break that. The drawing is `aria-hidden`: the lists below are its accessible form. On a narrow screen it keeps its size, scrolls sideways and opens on the artist.
- The search page is the app shell, `X-Robots-Tag: noindex` (nginx).

## SSRF, headers, and other security baselines

- Never `fetch()` a user-supplied URL without `assertSafeUrl()` from `lib/security/urlValidation`. It blocks private IPv4/IPv6, link-local (`169.254.0.0/16` = cloud metadata), and enforces `https` in prod.
- `securityHeaders` Elysia plugin must stay mounted on the app (`X-Content-Type-Options`, `X-Frame-Options`, CSP, HSTS in prod). Don't remove from `index.ts`.

## Performance landmarks

- `refreshAllLinks` runs in parallel chunks of 5 with a 500ms inter-chunk delay. Don't revert to per-track sleeps.
- `findTrackLinks` and `searchItunes` (`services/trackLinksService.ts`) are memoized in `lib/cache/ttlCache` with 7-day TTL; a result cut short by a failed lookup is not cached. Multi-instance deployments will need Redis.
- Track links come from each platform's API (iTunes, Deezer, Spotify by ISRC): Odesli closed its keyless API on 2026-07-31. A kept track's Deezer and Spotify links come from its ISRC (the play's, `radio_play.isrc`, else the stored one): the pipeline acquires every track from its Deezer page, so `/track/isrc:` finds the very recording the antenna plays (60/60 on 2026-10-04, where the title search picked another version for 16 of 59); the title search is only the fallback. Spotify search needs the app owner to hold Premium (development mode, since February 2026), otherwise it answers 403 and the other links still land.
- **A kept track plays on YouTube** (`youtubeService`, `youtubeLinks`). Its stored `youtube_url` is a search; the listing serves the song's **Art Track** instead once one is verified: the video YouTube builds from a distributor's delivery (ISRC and release), whose description names the recording « Title · Artist ». A result counts only when that line is the kept track: the same title once « (feat. …) » and a remaster are set aside, never a looser match (« Locked Out » is not « Locked Out (Smash The Lock) »), and credits that begin with the kept artist. Measured on 93 kept tracks on 2026-10-05: 60 found, none wrong. One lookup per song (`youtube_link`, keyed by `songKey`), shared by every listener: at the like, then an hourly run that stops at the quota.
- **YouTube's limits are load-bearing.** search.list has its own bucket of 100 calls a day; videos.list draws one unit per 50 ids on the 10,000 of the other methods ([quota costs](https://developers.google.com/youtube/v3/determine_quota_cost)). The quota grows with the songs the antenna adds, not with listeners; past it, the quota extension form ([audit](https://developers.google.com/youtube/v3/guides/quota_and_compliance_audits)). API data is refreshed or deleted within 30 days (Developer Policies III.E.4.d): stored videos are asked again with videos.list after 25 days, one gone is forgotten, and a link older than 30 days is never served. The legal page links YouTube's Terms of Service and the Google Privacy Policy (III.A.1-2). The key (`YOUTUBE_API_KEY`) never reaches a log, not even in a network error's URL; unset, every track opens its search.

## What NOT to do

- Don't re-introduce unused deps (`axios`, `cheerio`, `@tanstack/react-query`, `react-router-dom`, `@elysiajs/cron`, `class-variance-authority`, `dayjs`, `react-intersection-observer`) — they were removed in the May 2026 audit. Use existing alternatives.
- Don't write per-package `pnpm-lock.yaml` or `bun.lock` — the root pnpm-lock is authoritative.
- Don't disable `requireEmailVerification` unless a temporary migration window is needed (and roll back immediately).
- Don't bypass `securityHeaders` plugin or the rate limits in Better Auth.

## ESLint typed rules

Typed rules (`recommendedTypeChecked`, `no-floating-promises`, `no-misused-promises`, `no-unsafe-*`…) are at `error` on `apps/*/src` and `packages/*/src`. Intentional fire-and-forget promises get `void`.

## Dependencies

Renovate owns dependency PRs and auto-merges the safe ones once the required checks pass; `renovate.json` is the policy, the Dependency Dashboard issue lists what is pending. Dependabot is kept for security alerts only — don't re-add `.github/dependabot.yml`. A major bump goes in its own PR.

## Scaling

Caches and rate-limit buckets are in-process on purpose (`CacheStore<V>` in `lib/cache/ttlCache.ts`). The tiers, their listener triggers and the Redis migration list are in `docs/scaling-roadmap.md`; don't build a tier before its trigger fires.
